### Q3：默认只删历史，工作区清理单独勾选（B）

- 归档保留历史、代码、分支、上传与产物；具体状态判定和跨 cwd 关联仍需细化。

## 第 4 轮结论：缓存容量与清理（已确认）

owner：Q8、Q9 采用推荐 A；Q10 选择 B。

- Q8=A：默认浏览器每账号全局最多 1000 条缓存消息、20 MiB，任一达到即淘汰；不另设每对话上限、对话数量上限或按日期过期。消息计数包括完整用户消息、助手消息及工具摘要，不计流式片段。

## 第 9 轮结论：激活判定与清理时机（已确认）

owner：Q22、Q23 均同意推荐 A。

## 缓存策略汇总（截至第 9 轮）

- 浏览器缓存是非权威副本；Pi 原生历史在 VM；Web 服务器不持久化正文。
- 账号／VM 环境隔离。退出保留磁盘缓存，身份验证后才展示；确认换绑环境后清除旧环境缓存。
- 默认每账号最多 200 MiB 或 20000 条缓存消息，任一达到即淘汰；可调整。聊天正文及简短工具摘要可缓存，不保存文件原件、完整工具输出或授权 Token。
- 当前对话优先；近 7 天有成功发送消息的最多 5 个未归档对话，后台各预取最新 100 条。浏览器缺少可信激活记录时不臆测热度，不为热度记录新增跨设备服务；预取不更新激活计时。
- 超过 7 天的聊天缓存可在启动／空闲时清理；当前阅读不被打断；未超期内容在容量压力下优先淘汰最久未访问的对话，单对话过大时裁剪更早消息。
- 缓存先显示、VM 增量核对；完整原生历史向上滚动按需加载，保留阅读位置，长列表视口渲染。
- 冷对话仍跟踪必要任务状态，不自动同步全部正文。离线只读／可编辑草稿，不排队执行操作，重连后用户明确发送。
- 文字草稿单独保存，默认清缓存不清草稿；确认消息接收后只清对应已发送版本。
- 上述为规格决定，不代表已有代码实现完毕。

## 架构复核议题（owner 提出，尚未决定）

owner 提问：只有两名用户，是否无需独立集中 Web Server，每台用户 VM 自己提供网页入口即可？本轮先分析，不视为已批准迁移或取消 Gitea。

- 当前代码支持 web/host/relay/all 角色，Web 与 Host 的物理部署并非必须分机。当前集中入口来源于既有 Gitea→固定 VM 路由要求，不是 Pi 历史或 worktree 功能本身需要。
- 建议候选：每 VM 部署现有 Web 与 Host 两个独立服务，Web 仅连接本机 Host，Host 仅监听 loopback；浏览器访问自己的 VM 入口。保留进程边界，避免重启 Web 杀掉 Pi。不要直接把 main.js all 当作等价替代，它的统一 shutdown 会关闭 Host/Pi。
- 可取消中心用户→远端 Host 路由／跨 VM 桥接的必要性，但仍需本机入口认证和 owner 授权。Gitea 可保留为每 VM 的登录身份源，需拒绝其他 Gitea 用户，不将“登录成功”误作“本 VM 所有人”。身份方案尚待 owner 决定。
- 模型／搜索 Relay 与 Web 拓扑独立；如保留集中上游密钥，Relay 仍留管理员服务，不把上游密钥复制进用户 VM。
- 本机文件服务同源入口可作为后续薄适配，复用 TransferServer；无需重写上传协议或增加中心文件中转。
- 本地浏览器缓存、原生历史、worktree、Arena 式 UI 等需求不依赖集中 Web。独立入口带来分 origin 缓存和多个部署实例，也失去天然统一入口与集中路由管理；是否接受需确认。


## 2026-09-19 架构决定：统一入口 + 私网用户 VM（已确认）

owner 对“统一轻量网关 + 每用户独立 VM + 文件流经入口”的建议回复“同意，请更改 spec”。

- 保留现有中央 Web 作为统一静态页面、Gitea 登录、固定路由和聊天／文件流式转发入口，不另造 Agent 平台。
- 默认浏览器 → 统一 Web → 私网 Host／Transfer → Pi，不增加必需的 VM 内 Web 层。
- 统一公网应用入口 HTTPS/WSS；VM Host／文件端口仅私网可达并限制来源。新增用户配置 VM 和路由，不逐 VM 开公网端口／证书。
- 原“文件字节不经 Web”要求被替代；新要求是有界流式转发、无中央持久化／临时落盘正文、无任意目标代理。VM 端继续复用原有文件传输和安全发布。
- Host/Pi 独立于网关生命周期，网关重启不杀任务；可选 Relay 独立、上游密钥不下放 VM。
- 主 SPEC、产品排期、拓扑和 ADR-0010 已同步；ADR-0009 部分废止，旧部署／协议文档标注迁移边界。
