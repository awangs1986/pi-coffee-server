# Pi 0.99 and plugin upgrade plan: P0–P10

Status: P0–P9 implemented as a pre-merge candidate; see [evidence](pi-099-p0-p9-evidence.md). P10 deployment is pending. Date: 2026-09-30.

Owner request: sequence the Pi runtime and every active plugin upgrade, preferring upstream capabilities and native package management. This plan follows the [impact audit](../research/pi-099-upgrade-impact-20260930.md). [Server #4](https://github.com/awangs1986/pi-coffee-server/issues/4) records the previous partial rollout; it does not prove the remaining tasks below are complete. New implementation work should have linked Issues with scope and acceptance evidence before changes begin.

## Upgrade policy and target composition

Prefer Pi core functionality first, original upstream plugins second, and Coffee implementation only for product-specific behavior that those interfaces do not provide. `pi-web-access` and `pi-subagents` are independently maintained community packages, not built-in Pi tools. Preserve Host/Web/native Codex/Claude boundaries, VM ownership, Conversation folders, authentication and model defaults.

| Component | Observed baseline | Planned target |
| --- | --- | --- |
| Host/root Pi | 0.99.1 | Exact 0.99.1 baseline, public RPC integration corrected |
| Selected child Pi | 0.87.1 | Same verified 0.99.1 runtime as its parent |
| Separate terminal Pi installation | 0.86.1 | 0.99.1, selected executable and package composition verified |
| pi-subagents | 0.63.0 through legacy Coffee bridge | Original upstream 0.73.1 through native Pi package loading |
| pi-web-access | 0.27.0 | Original upstream 0.34.0 with explicit activation policy |
| pi-coffee-harness | 0.1.4 | Next version only if code/configuration contract changes; use native discovery where it meets policy |
| pi-coffee-lsp | 0.4.4 | Retain or release the smallest necessary compatibility update |
| context-handoff | 0.2.0-experimental.3 | Retain or release the smallest necessary compatibility update; stays experimental |
| Legacy aggregate | pi-coffee at 1ec49a9 | Remove after every live consumer has a replacement |

Versions are the researched candidates, not moving `latest` declarations. Recheck registries at P0; a newer release is a candidate requiring review, not an automatic scope change. No forced version bump for an unchanged Coffee package, and no bulk language-server upgrade merely because Pi changes. Disabled historical pi-lens/context-fold/MCP-adapter integrations are not reactivated.

Pi 0.99 documents `pi update` for core, `pi update --extensions` for installed packages, and `pi update <source>` for one package. Versioned npm sources and Git refs remain pinned during reconciliation. Advancing a pin requires explicitly selecting the new version. Use native installation/discovery, with exact npm versions or verified release directories. Coffee release tarballs remain immutable; until registry publication exists, install verified artifacts into versioned directories and register their package roots. Do not pass a tarball URL to Pi assuming it is an npm archive: native URL sources are treated as Git sources.

For terminal installations, use the official updater where it supports the required installation method and target; otherwise use the documented official npm distribution at the exact version. For a Server-bundled runtime, update its dependency lock and deploy a built release instead of running a self-updater inside a production release. Avoid `pi update --all` during this migration because it mixes independently testable changes.

Sources: [native package management](https://github.com/earendil-works/pi/blob/v0.99.1/packages/coding-agent/docs/packages.md), [update commands](https://github.com/earendil-works/pi/blob/v0.99.1/packages/coding-agent/docs/cli.md#update-pi-or-packages), [Coffee release guide](https://github.com/awangs1986/pi-coffee/blob/b9063e4f003fcf13f1b0cc934a3500655dfb55a3/docs/releases/README.md).

## Dependencies and scope limits

Recommended execution order is P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8 → P9 → P10. P3 may prepare native declarations, but must not turn on duplicate old/new loaders before each component migrates. P2 is not complete toolchain parity by itself: P4 must prove the launched child uses the selected runtime, and P9 removes the obsolete dependency.

Prefer supported upstream options and public hooks to copied implementations. If an upstream package lacks a required product behavior, record the gap and add the smallest independent integration at the correct boundary. Do not fork the upstream web/subagent package as the default response. Context output limits are measured at the model-facing result, not inferred from a package's large default truncation limit. Required summary/pointer or lifecycle gaps are release blockers, not hidden omissions.

Codemode, MCP, virtual-model routing, new default models and a new Handoff algorithm are not required for this upgrade. Native tool discovery can be adopted without enabling all of them. If codemode is later proposed, separately test nested tool boundaries, structured-result transformations, event/usage accounting, cancellation and output budgets before activating it.

The linked evidence records implementation checks; this plan alone is not deployment evidence. Keep deterministic tests focused on changed public contracts; use a small end-to-end smoke run rather than repeating broad paid evaluations. No new UI layout, VM topology or Host-as-plugin migration is part of P0–P10.
