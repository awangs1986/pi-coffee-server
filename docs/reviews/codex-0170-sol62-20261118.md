# Codex 0.170.0 / GPT-6.2 qualification

Tracking: [Server #168](https://github.com/awangs1986/pi-coffee-server/issues/168).
Source candidate: Server 1.05. Installation and source verification do not imply
loaded-Host activation. Production activation evidence belongs to the Issue.

## Upstream and intended change

On 2026-11-18, npm stable `@openai/codex` resolves to 0.170.0. The package is
installed with an exact version in a separate runtime directory; previous
0.163.0 and 0.159.1 installations are retained. The prepared wrapper selects
`gpt-6.2-sol` / `medium`, with the same unrestricted native permission policy.
No native credential, provider endpoint or historical task preference is changed
by installing the candidate.

Official [model documentation](https://learn.chatgpt.com/docs/models?surface=cli)
identifies `gpt-6.2-sol` and `gpt-6.2-astra`; the
[changelog](https://learn.chatgpt.com/docs/changelog) records their November 17
availability. Coffee retains its existing context presets rather than silently
enabling the models' larger upstream window.

## Executed evidence

- The isolated installed-CLI compatibility probe passed initialization, generated
  compact/resume/steer/token-usage protocol checks, model metadata and Skill
  catalog shape. It created zero threads and submitted zero model turns.
- A separate metadata-only connection using the current owner's configured
  native home confirmed both requested model IDs, the candidate wrapper's Sol
  6.2 / medium defaults and the preserved standalone-search capability. It
  created zero threads and submitted zero model turns. Provider credentials and
  account details were not printed or copied into source.
- The authenticated Host HTTP/WS regression rejected 0.170.0 before the readiness
  change. After adding that exact stable version, all 37 native-engine tests
  passed, including discovery, empty Work opening and rejection of unknown patch
  and prerelease versions. An initial pre-build run failed at fixture startup;
  after the documented build the failure isolated the actual version gate.
- One serial installed-CLI thread used only a loopback Responses fixture. After
  selecting Sol 6.2 / high, two factory reopenings retained that model/effort and
  sent them on subsequent synthetic requests. This exercises preservation of an
  explicit task selection; it does not change the medium startup default. No
  production task, login or paid model was used.

Complete repository verification, serial review, publication, independent
fresh-clone verification and staged release identity must be recorded separately
before service activation. A model catalog alone does not prove quota, a real
provider answer, real compaction, search invocation or every optional API.

## Scope boundaries

NativeAgentFactory accepts the qualified stable version; unknown versions and
prereleases remain unavailable. The actual model picker remains dynamic. No
hardcoded sibling model, pricing or context change was added to the Browser.
Existing per-task preferences, native login, provider search opt-in, permissions
and the separately pinned Handoff preparation model remain intact. Goal budget
and additional command-inventory work under #163 is not claimed complete here.

Before activation, privately back up changed configuration, retain the old
service/CLI release and take a consistent native-store snapshot in the maintenance
window. Avoid interrupting running tasks. A binary rollback does not roll back
native data formats; do not overwrite newer histories with an older snapshot.
After activation, verify normal health, effective Host command/version, scoped
engine availability, native Sol/Astra catalog and Sol default without sending a
model prompt or automatically reopening a batch of conversations.
