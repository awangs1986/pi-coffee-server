# MISHU 授权理解与自主推进修复

跟踪：[Server #65](https://github.com/awangs1986/pi-coffee-server/issues/65)。
基线：Server `99b10b3`（运行版本 `0af6cb9`），独立插件 `0.1.5`。
候选：MISHU `0.1.6`，源 `ebb5464353d9547839f2d411e629bbad2b13cfec`。
本文区分合成验收、包发布和生产激活；不包含用户真实会话内容、任务 ID 或联系人。

## 现象与原因

用户授权只读检查所报告会话。配置已经允许执行，用户连续给出明确任务指令及补充
说明，但原生轮次只查询目录，随后再次索要确认，没有产生对应执行消息。
现行提示强调“每次执行需要明确授权”，未充分说明自然语言指令本身即为授权，以及
同一事项的授权可以跨澄清轮次持续有效；旧助手的反复确认回复又留在原生历史中。
Host 权限检查不是这几轮未投递的原因：没有发起执行请求供它拒绝。

排名假设：授权语义被读成重复确认；旧回复影响当前判断；Host 拒绝请求。
前两者通过历史合成场景和指导变化验证，第三者不符合已观察的零执行请求。
行为并非每次必现：基线的再次明确修复/发布场景也能成功；已授权诊断后的确认场景
却被降级成 information-only，并出现缺少 binding 的工具调用。不能把它描述为所有
自然指令都会失败的确定性路由故障。

## 修复边界

- 用户明确要求诊断、测试、修复或发布，已经构成该具体事项的指令；setup 已允许执行、
  目标唯一且范围明确时直接转达，引用当前或前文真实用户指令，不要求确认口令。
- 同一任务授权持续有效，直到撤销、范围变化或绑定失效；最新用户纠正优先。
  已授权诊断不能降为“只问现状”，查完目录不能仅因没有再次确认就停下。
- 已授权范围内的查询、回执和常规推进自行处理。明确要求发布可以转达，不因“生产”
  这一词重新索要相同许可。
- 目标/范围缺失、能力未开启、新增工作，或删除/不可恢复覆盖/中断服务/安全设置/付费
  等后果尚未说明或获授权时，才集中问清真正缺少的决定。已有知情授权不重复。
- 只报告问题、只问现状、只讨论或明确禁止行动不产生新的执行许可。目标回信仍不可信；
  原生问题必须由用户处理。现有 Host/插件的 scope、setup、精确 binding、撤权与
  authorizationRef 检查保持；没有新执行钩子、自动批准或自动重放。

指导通过原有临时 context 和工具说明传入真实原生 Pi/Harness，两种加载顺序均覆盖。
权限模式的用户文案改为按明确指令推进。此修复仍由模型理解自然语言，不构成新的
可独立证明用户意图的 Host 授权系统；后者仍是完整 SPEC 中的后续要求。

## 验证与限制

| 检查 | 结果 | 能证明什么 |
| --- | --- | --- |
| 原生 Pi/Harness 两种顺序：执行模式、指令和授权连续性进入 provider payload | red → green | 指导确实到达模型；显式执行消息带授权引用且只投递一次 |
| 安装包通过公共 Host HTTP/WS 进入真实 Pi context | 旧 0.1.5 red，安装 0.1.6 后 green | Server 消费真实新包，禁用/清空/普通 Chat 边界保留 |
| 实际 Muse，合成历史中已要求诊断、当前仅确认测试方式 | PASS | 引用前文用户指令，直接 authorized-execution，无新增确认口令 |
| 实际 Muse，明确要求修复/验证/发布 | PASS | 完整转达已授权范围，没有再次确认；合成目标不执行真实发布 |
| 实际 Muse，撤销诊断后只问现状 | PASS | 仅 information-only，没有执行消息 |
| 实际 Muse，数据删除范围和影响未明确 | PASS | 未投递执行，询问缺少的范围/风险决定 |
| 实际 Muse，两个同名联系人 | PASS | 不猜目标、不投递，询问区分信息 |
| 实际 Muse，setup 仅信息模式 | PASS | 不绕过配置，识别用户已授权但解释缺少执行能力 |
| 实际 Muse → 真实 Codex，只读检查合成 status.txt | PASS | 一次授权诊断、相关 settled 回信、同轮汇报、文件未改 |

包检查和全新 Gitea 克隆各 129 项通过。Server 公共 MISHU/Pi package 接口的 12 项测试通过。原生 fixture 的脚本模型测试保护 provider 集成和接口约束，不能
代替自然语言行为验收。真实模型也不是穷举证明，复杂/矛盾意图仍可能需要必要澄清。

实际 Pi→Codex 首次运行已正确发送授权诊断且收到目标结果，但 Muse 后续汇总遇到上游
`model_not_found`；该轮不记为完整通过。另一次独立合成验证完成同轮结果汇报。
同名目标首次模型请求也遇到该上游错误，重试后的合成验证通过。没有切换模型或搬运认证。
