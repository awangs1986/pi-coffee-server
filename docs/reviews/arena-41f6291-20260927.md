## Standards

- **P2:** The new Pi rejection test only called the Session directly. It did not demonstrate the required public WebSocket error envelope, request correlation or browser recovery. Added tests run the real RPC client against a subprocess fixture through Host WebSocket and drive the actual browser controller.
- **P2:** Surfacing a rejected queued command exposed a browser state defect: every `operation_failed` ended the visible run even while the original Pi run continued. The browser now correlates queued input requests and retains the active reply and Stop control when those inputs fail.

Final independent standards re-review: **PASS**, no remaining actionable finding.

## Spec

Initial finding, resolved:

- **P2:** Rejecting an extension command submitted through `steer` or `follow_up` hid Stop and queue controls and could split a continuing assistant reply. That contradicted the active-Session queue contract in `docs/protocol.md` and the running/error distinction in `docs/spec/native-agent-browser.md` (NB-07).

Both queue modes now preserve the running turn. If Host instead accepts the input as a new `prompt` because the prior turn ended, a rejection correctly releases the browser for retry. A known rejection clears its pending delivery marker, so reconnect does not label it uncertain or automatically replay it.

Final independent spec re-review: **PASS**, no remaining concrete blocker.

The adapter still isolates Pi-specific behavior. Both inspected pinned versions, 0.84.4 and 0.87.1, discard `success:false` in the public RPC client prompt/queue wrappers. The adapter checks the raw response through the existing client transport, retaining request IDs, timeouts and process-failure handling. This dependency on the pinned client's `send` method must be checked on future Pi upgrades.
